## 1. 임베딩이란 무엇인가?

### 비유로 이해하기

당신이 도서관 사서라고 상상해보자. 수만 권의 책이 있고, 특정 주제의 책을 찾아야 한다.

**전통적인 방법**: 책 제목에 "요리"라는 단어가 들어간 책만 찾는다.
→ "요리"가 들어가지 않은 "쿠킹", "레시피", "음식 만들기" 책은 찾지 못한다.

**임베딩 방법**: 모든 책의 내용을 '의미 공간'이라는 가상의 지도 위에 배치한다.
→ 비슷한 주제의 책들은 지도 위에서 서로 가까이 위치한다.
→ "요리"로 검색하면 "쿠킹", "레시피", "음식 만들기" 책도 함께 찾을 수 있다.

### 기술적 정의

임베딩(Embedding)은 텍스트, 이미지, 음성 등 비정형 데이터를 **고정된 길이의 숫자 배열(벡터)** 로 변환하는 기술이다. 이 벡터는 원본 데이터의 '의미'를 수치적으로 표현한다.

```
"오늘 날씨가 좋다" → [0.023, -0.451, 0.789, ..., 0.312]  (384개의 숫자)
"날씨가 맑고 화창하다" → [0.019, -0.438, 0.801, ..., 0.298]  (비슷한 방향)
"파이썬을 배우고 있다" → [-0.612, 0.234, -0.089, ..., 0.567]  (다른 방향)
```

### 임베딩 벡터의 핵심 성질

1. **의미가 비슷한 텍스트는 벡터 공간에서 가깝다**
2. **의미가 다른 텍스트는 벡터 공간에서 멀다**
3. **벡터 간 거리/각도를 계산하여 '의미적 유사도'를 수치로 표현할 수 있다**

이것이 바로 임베딩의 마법이다. 컴퓨터는 단어의 의미를 이해하지 못하지만, 벡터의 수학적 연산을 통해 '의미적 가까움'을 계산할 수 있게 된다.

## 2. 왜 임베딩을 사용하는가?

### 2.1. 의미적 검색 (Semantic Search)

**문제**: 사용자가 "돈을 돌려받고 싶어요"라고 검색한다.
- 키워드 검색: "환불"이라는 단어가 없으므로 검색 결과 0건.
- 임베딩 검색: "환불은 구매 후 7일 이내에 가능합니다"라는 문서를 찾는다.

```python
# 개념 코드 (실제 동작 코드는 아래 섹션 참조)
query = "돈을 돌려받고 싶어요"
docs = ["환불은 구매 후 7일 이내에 가능합니다", "배송은 3~5일 소요됩니다"]

query_vec = embed(query)     # [0.12, -0.34, ...]
doc_vecs = [embed(d) for d in docs]

similarity(query_vec, doc_vecs[0])  # 0.72 ← 높음! 의미가 통함
similarity(query_vec, doc_vecs[1])  # 0.08 ← 낮음. 주제가 다름
```

### 2.2. 대규모 텍스트 분류 및 클러스터링

수천~수만 개의 문서를 사람이 일일이 분류하는 것은 불가능하다. 임베딩을 사용하면:

1. 모든 문서를 벡터로 변환한다.
2. 벡터 공간에서 가까운 문서끼리 자동으로 그룹화한다.
3. 각 그룹의 대표 키워드를 추출해 자동 라벨링한다.

→ 고객 문의를 "환불/배송/계정/기타"로 자동 분류하는 등의 업무에 활용된다.

### 2.3. 추천 시스템

"이 글과 비슷한 다른 글", "이 제품과 비슷한 다른 제품"을 찾는 데 탁월하다.

```
사용자가 읽은 문서의 임베딩을 구한다
→ 벡터 공간에서 가장 가까운 다른 문서들을 찾는다
→ "비슷한 문서"로 추천한다
```

### 2.4. RAG (Retrieval-Augmented Generation)

LLM(ChatGPT, Claude 등)의 가장 큰 약점은 두 가지다:

1. **환각(Hallucination)**: 모르는 내용을 그럴듯하게 지어낸다.
2. **지식의 시점 제한**: 학습 시점 이후의 정보는 알지 못한다.

**RAG는 이 문제를 임베딩으로 해결한다**:

```
질문: "2026년 5월 기준 우리 회사 환불 정책은?"
→ 1. 질문을 임베딩 벡터로 변환
→ 2. 회사 내부 문서 저장소에서 가장 관련 있는 문단 검색 (임베딩 유사도)
→ 3. 검색된 문단을 LLM에게 "참고 자료"로 제공
→ 4. LLM: "2026년 5월 기준 환불은 구매 후 14일 이내 가능합니다. (출처: 사내 정책 문서 v3.2)"
```

### 2.5. 비용 효율성

GPT-4나 Claude Opus에 모든 문서를 매번 전부 보내는 대신, 질문과 관련된 부분만 임베딩 검색으로 추려서 보낼 수 있다.

- **Without RAG**: 50페이지 문서 전체를 매 질문마다 전송 → 토큰 낭비
- **With RAG**: 질문과 관련된 2~3문단만 전송 → 토큰 90% 이상 절약

## 3. 임베딩 vs 전통적인 텍스트 처리

### 3.1. 키워드 검색 (TF-IDF, BM25) vs 의미 검색 (Embedding)

| 특성 | 키워드 검색 | 임베딩 검색 |
|------|------------|-----------|
| 매칭 방식 | 단어의 정확한 일치 | 의미적 유사도 |
| "기쁘다"로 "행복하다" 검색 | 찾지 못함 | 찾을 수 있음 |
| "bank"(은행) vs "bank"(강둑) | 구분 불가 | 문맥으로 일부 구분 가능 |
| 다국어 검색 | 불가능 (번역 필요) | 가능 (의미 공간 공유) |
| 속도 | 빠름 | 상대적으로 느림 |
| 구현 복잡도 | 낮음 | 중간 |

### 3.2. 구체적인 예시

```
질문: "컴퓨터가 느려졌을 때 어떻게 하나요?"

[키워드 검색 결과]
- "컴퓨터"와 "느려"가 포함된 문서만 검색됨
- "PC 성능 저하 해결 방법" ← "컴퓨터"라는 단어가 없어서 누락!

[임베딩 검색 결과]
- "PC 성능 저하 해결 방법" ← 의미가 유사하므로 상위 노출!
- "노트북 속도 개선 팁" ← 이 문서도 찾을 수 있음!
- "윈도우 부팅이 오래 걸릴 때" ← 역시 찾음!
```

## 4. 임베딩의 실제 활용 사례

### 4.1. 고객 지원 자동화

```
고객 문의 → 임베딩 변환 → FAQ 벡터 DB 검색 → 가장 유사한 답변 자동 응답
```

- 처리 시간: 수 초 이내
- 정확도: FAQ와 유사한 질문에 대해 90%+
- 인간 상담원 연결 전 1차 필터링으로 비용 절감

### 4.2. 중복/유사 문서 탐지

```
모든 문서의 임베딩을 구한다 → 벡터 간 거리가 매우 가까운 쌍을 찾는다 → "유사 문서"로 플래그
```

- 표절 검사
- 코드 저장소에서 중복 코드 탐지
- 뉴스 기사 중복 필터링

### 4.3. 이미지 검색 (멀티모달 임베딩)

CLIP 같은 멀티모달 모델을 사용하면 텍스트와 이미지를 같은 벡터 공간에 배치할 수 있다.

```
"빨간 운동화" (텍스트) → [0.1, 0.3, ...]
🟥👟 (이미지) → [0.09, 0.31, ...]  ← 벡터가 매우 가까움!
```

### 4.4. 이상 탐지 (Anomaly Detection)

```
정상 로그 메시지들의 임베딩을 구한다 → 중심점을 계산 → 
새 로그 메시지가 중심점에서 너무 멀면 "이상"으로 감지
```

- 서버 에러 로그 탐지
- 사기 거래 패턴 탐지
- 제조 공정 불량 예측

## 5. RAG (Retrieval-Augmented Generation)

### 5.1. RAG의 동작 원리

RAG는 "검색(Retrieval)" + "생성(Generation)"의 합성어다.

```
                        ┌─────────────────────┐
                        │   문서 저장소        │
                        │  (PDF, 웹, DB 등)    │
                        └────────┬────────────┘
                                 │
                                 ▼
                        ┌─────────────────────┐
                        │  임베딩 모델         │
                        │  (문서 → 벡터 변환)  │
                        └────────┬────────────┘
                                 │
                                 ▼
                        ┌─────────────────────┐
 사용자 질문            │   벡터 데이터베이스   │
     │                  │  (FAISS, Chroma 등) │
     ▼                  └────────┬────────────┘
┌─────────────┐                  │
│ 임베딩 모델  │                  │ 유사도 검색
│ (질문→벡터)  │                  │
└──────┬──────┘                  │
       │                         │
       └─────────┬───────────────┘
                 │
                 ▼
       ┌─────────────────────┐
       │  검색된 관련 문서     │
       │  (Top-K 결과)        │
       └──────────┬──────────┘
                  │
                  ▼
       ┌─────────────────────┐
       │  LLM에게 전달        │
       │  (질문 + 관련 문서)   │
       └──────────┬──────────┘
                  │
                  ▼
       ┌─────────────────────┐
       │  최종 답변 생성      │
       │  (문서 기반, 환각↓)  │
       └─────────────────────┘
```

### 5.2. RAG가 해결하는 문제

| LLM 단독 사용 | RAG 사용 |
|--------------|---------|
| "우리 회사 환불 정책은요?" → 지어냄 | 내부 문서 검색 → 정확한 정책 기반 답변 |
| 2024년 이후 사건에 대해 모름 | 최신 문서를 저장소에 추가하면 즉시 반영 |
| 출처를 알 수 없음 | "이 답변은 문서 X, Y를 기반으로 합니다" |
| 모든 대화에 전체 컨텍스트를 보내야 함 | 관련 부분만 검색해서 토큰 절약 |

### 5.3. RAG가 특별히 유용한 상황

- **기업 내부 지식 베이스**: 사내 위키, 매뉴얼, 정책 문서 기반 Q&A
- **법률/의료 문서**: 최신 판례, 의학 논문 기반 답변 (환각이 치명적인 분야)
- **제품 문서**: API 문서, 사용자 매뉴얼 기반 기술 지원
- **교육**: 교과서, 강의 노트 기반 질의응답

## 6. 코드로 이해하는 임베딩

### 6.1. 환경 설정

```bash
uv add sentence-transformers scikit-learn
```

### 6.2. 첫 번째 임베딩 생성

```python
from sentence_transformers import SentenceTransformer

# 모델 로드 (최초 1회 다운로드, 약 80MB)
model = SentenceTransformer("all-MiniLM-L6-v2")

# 텍스트를 벡터로 변환
texts = [
    "오늘 날씨가 정말 좋다",
    "현재 기온은 20도이며 맑은 하늘입니다",
    "파이썬은 배우기 쉬운 프로그래밍 언어입니다",
]

vectors = model.encode(texts)
print(vectors.shape)  # (3, 384) ← 3개 문장, 각 384차원 벡터
print(vectors[0][:5])  # [ 0.023, -0.451, 0.789, -0.112, 0.312 ]
```

### 6.3. 의미적 유사도 측정

```python
import numpy as np

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    """코사인 유사도: 1에 가까울수록 의미가 유사"""
    return float(np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b)))

# 의미가 비슷한 두 문장 → 높은 유사도
sim_weather = cosine_similarity(vectors[0], vectors[1])  # ≈ 0.7~0.8

# 의미가 다른 문장 → 낮은 유사도
sim_diff = cosine_similarity(vectors[0], vectors[2])     # ≈ 0.1~0.3

print(f"비슷한 문장 유사도: {sim_weather:.3f}")
print(f"다른 문장 유사도:   {sim_diff:.3f}")
```

### 6.4. 의미 검색 구현

```python
from src.embedding_study import SentenceEmbedder, InMemoryVectorStore

embedder = SentenceEmbedder()

# 지식 베이스 구축
documents = [
    "환불은 구매 후 7일 이내에 가능합니다.",
    "배송은 영업일 기준 3~5일 소요됩니다.",
    "회원가입은 이메일 또는 SNS 계정으로 가능합니다.",
]

ids = ["doc_1", "doc_2", "doc_3"]
vectors = embedder.encode(documents)

store = InMemoryVectorStore()
store.add(ids, documents, vectors)

# 의미 검색
query = "돈을 돌려받고 싶어요"  # "환불"이라는 단어가 없음!
query_vec = embedder.encode([query])[0]
results = store.search(query_vec, top_k=1)

print(f"검색 결과: {results[0][1]}")  # "환불은 구매 후 7일 이내에 가능합니다."
print(f"유사도: {results[0][2]:.3f}")  # 0.7 이상
```

### 6.5. RAG 파이프라인

```python
from src.embedding_study import SentenceEmbedder, RAGPipeline, build_knowledge_base

embedder = SentenceEmbedder()
store = build_knowledge_base(embedder)
rag = RAGPipeline(embedder, store)

result = rag.ask("환불은 어떻게 하나요?", top_k=2)

print("=== 검색된 문서 ===")
for doc in result["documents"]:
    print(f"  [{doc['score']:.3f}] {doc['text']}")

print("\n=== LLM에 전달할 프롬프트 ===")
print(result["prompt"])
```

### 6.6. 실제 LLM과 연동하기 (Claude API)

```python
from anthropic import Anthropic

client = Anthropic()  # ANTHROPIC_API_KEY 환경 변수 사용

result = rag.ask("환불은 어떻게 하나요?")
response = client.messages.create(
    model="claude-sonnet-4-6",
    max_tokens=1024,
    messages=[{"role": "user", "content": result["prompt"]}],
)

# 검색된 문서를 바탕으로 정확한 답변 생성
print(response.content[0].text)
```

## 7. 모델 선택 가이드

### 7.1. 주요 임베딩 모델 비교

| 모델 | 차원 | 크기 | 특징 | 추천 용도 |
|------|------|------|------|----------|
| `all-MiniLM-L6-v2` | 384 | 80MB | 가장 빠름, CPU 충분 | 학습, 프로토타입 |
| `all-mpnet-base-v2` | 768 | 420MB | 품질 ↑, 속도 ↓ | 실무 서비스 |
| `multilingual-e5-large` | 1024 | 560MB | 다국어 지원 | 한/영 혼합 서비스 |
| `BGE-M3` | 1024 | 568MB | 다국어 + 8192 토큰 | 긴 문서 |
| `intfloat/multilingual-e5-large-instruct` | 1024 | 1.1GB | 최고 품질, instruction 따름 | 엔터프라이즈 |
| `text-embedding-3-small` | 512 | API | OpenAI 호스팅 | 서버리스 |
| `text-embedding-3-large` | 3072 | API | OpenAI 최고 품질 | 고품질 필요시 |

### 7.2. 선택 기준

1. **한국어 지원**: `multilingual-e5-*`, `BGE-M3`, `ko-sroberta-multitask`
2. **서버 비용**: CPU-only 서버 → `all-MiniLM-L6-v2`. GPU 서버 → `multilingual-e5-large`
3. **문서 길이**: 토큰 제한 확인. 대부분 512토큰, 긴 문서는 `BGE-M3`(8192토큰)
4. **응답 속도**: 실시간 검색 → 경량 모델. 배치 처리 → 대형 모델도 무방

### 7.3. 이 프로젝트에서 사용하는 모델

`all-MiniLM-L6-v2` — Sentence-BERT 계열 경량 모델:
- **384차원**: 벡터 하나당 384개의 float 값
- **80MB**: 가볍고 다운로드가 빠르다
- **영어 전용**: 한국어는 자동 번역 후 처리되거나 의미적 유사성만 포착
- **CPU에서 충분히 빠름**: 초당 수백 문장 처리 가능

## 8. 자주 묻는 질문

### Q1. "임베딩은 결국 LLM인가요?"

아니다. 임베딩 모델과 LLM은 다른 종류의 모델이다:

| | 임베딩 모델 | LLM (GPT, Claude 등) |
|---|---|---|
| 출력 | 고정 길이 벡터 (숫자 배열) | 가변 길이 텍스트 |
| 목적 | 의미를 수치로 표현 | 텍스트 생성, 대화 |
| 크기 | 수십~수백 MB | 수십~수백 GB |
| 속도 | 매우 빠름 (ms 단위) | 상대적으로 느림 (초 단위) |

두 모델은 함께 사용될 때 시너지가 있다: 임베딩이 "찾고", LLM이 "생성한다" (RAG).

### Q2. "왜 384차원인가요? 100차원이나 1000차원이면 안 되나요?"

차원 수는 트레이드오프다:
- **차원이 높을수록**: 더 세밀한 의미 구분 가능, 저장 공간↑, 검색 속도↓
- **차원이 낮을수록**: 저장 공간↓, 검색 속도↑, 의미 구분력↓

384차원은 Sentence-BERT 팀이 "가벼우면서도 대부분의 용도에 충분한 성능"을 내도록 실험적으로 결정한 값이다.

### Q3. "벡터를 저장하려면 어떤 데이터베이스를 써야 하나요?"

용도에 따라 다르다:

| 규모 | 추천 | 특징 |
|------|------|------|
| < 10만 건 | PostgreSQL + pgvector | 기존 DB에 통합 |
| 10만~100만 건 | Chroma | 경량, Python 친화적 |
| 100만~1억 건 | FAISS (Meta) | 초고속, C++ 기반 |
| > 1억 건 | Pinecone, Weaviate | 관리형 서비스, 확장성 |

### Q4. "한국어는 임베딩이 잘 안 된다는 얘기를 들었는데요?"

과거에는 그랬지만, 2024년 이후 멀티링구얼 모델의 등장으로 상황이 크게 개선되었다.

- `multilingual-e5-large`: 한국어 포함 100개 언어 학습
- `BGE-M3`: 중국어/영어 중심이지만 한국어도 양호
- `ko-sroberta-multitask`: 한국어 특화 모델

한국어 전용 태스크가 중요하다면 `ko-sroberta-multitask`나 `snunlp/KR-SBERT` 같은 모델을 검토한다.

### Q5. "임베딩 벡터는 어떻게 생겼나요?"

실제로 보면 이렇다:

```
[ 0.023456, -0.451234,  0.789012, -0.112345,  0.312678,
 -0.623456,  0.234567, -0.890123,  0.456789, -0.345678,
  ... 총 384개의 float32 값 ... ]
```

각 숫자는 -1~1 범위로 정규화된 경우가 많다. 이 숫자들은 사람이 해석할 수 없지만, 수학적으로는 의미 공간의 '좌표' 역할을 한다.

### Q6. "임베딩과 LLM 중 하나만 써야 한다면?"

둘은 상호 보완적이다:

- **텍스트 생성, 대화, 번역, 요약** → LLM
- **검색, 분류, 중복 탐지, 추천** → 임베딩
- **정확한 지식 기반 Q&A** → RAG (임베딩 + LLM)

하나만 선택해야 한다면 용도에 따라 결정한다. 하지만 실제 프로덕션 시스템에서는 대부분 RAG로 함께 사용한다.

## 부록: 용어 정리

| 용어 | 설명 |
|------|------|
| **임베딩 (Embedding)** | 데이터를 고정 길이 벡터로 변환하는 기술 또는 그 결과물 |
| **벡터 (Vector)** | 숫자의 배열. 예: [0.1, -0.3, 0.8] — 3차원 벡터 |
| **차원 (Dimension)** | 벡터의 길이. 384차원이면 384개의 숫자로 구성 |
| **코사인 유사도** | 두 벡터 간 방향 유사도 (1=같음, 0=무관, -1=반대) |
| **유클리드 거리** | 두 벡터 간 직선 거리 (0에 가까울수록 비슷함) |
| **벡터 DB** | 임베딩 벡터를 저장하고 유사도로 검색하는 데이터베이스 |
| **RAG** | 검색(Retrieval) + 생성(Generation). LLM 답변 전에 관련 문서 검색 |
| **청킹 (Chunking)** | 긴 문서를 임베딩하기 좋은 크기로 나누는 작업 |
| **Top-K** | 유사도 검색 결과 중 상위 K개 |
| **Sentence-BERT** | 문장 단위 임베딩에 특화된 BERT 변형 모델군 |
| **환각 (Hallucination)** | LLM이 사실이 아닌 내용을 그럴듯하게 생성하는 현상 |
